# Structured Asynchronous Logging

SwiftPY ships a dedicated non-blocking logging subsystem built on stdlib `logging`, `QueueHandler`, and `QueueListener` (`swiftpy.logging`). Application logs and framework diagnostics write to an in-memory queue so request coroutines never block on file writes, while background listeners flush and rotate targets cleanly on shutdown.

Quick imports:

```python
from swiftpy import Log
from swiftpy.logging import (
    DEFAULT_LOG_FORMAT,
    ChannelLogger,
    LogManager,
    parse_log_level,
    resolve_log_path,
)
```

---

## How Lifecycle & Queue Dispatch Work

When `Application` boots, `FrameworkServiceProvider` starts `LogManager` **first** (before database, cache, queue, or HTTP startup) via `await log_manager.astart()`, and stops/flushes it **last** during shutdown via `await log_manager.astop()`:

1. Each leaf channel (for example `"single"`, `"daily"`, or `"stderr"`) wraps its concrete stdlib handler inside a bounded `queue.Queue` (default `queue_size=10_000`), a `QueueHandler`, and a dedicated `QueueListener(..., respect_handler_level=True)`.
2. When your code calls `Log.info(...)`, `ChannelLogger` pushes a record into the queue and returns immediately without touching disk.
3. Multiple `Application` instances in the same Python process (such as concurrent test suites) isolate their own internal channel loggers and framework `'swiftpy.*'` handlers cleanly, restoring state on teardown without leaking into `logging.Logger.manager.loggerDict`.

## Configuring `config/logging.py`

Fresh projects created with `swiftpy new` include `config/logging.py`:

```python
# config/logging.py
from __future__ import annotations

from swiftpy import env

CONFIG = {
    "default": env("LOG_CHANNEL", "stack"),
    "level": env("LOG_LEVEL", "info"),
    "channels": {
        "stack": {
            "driver": "stack",
            "channels": ["single", "stderr"],
        },
        "single": {
            "driver": "single",
            "path": env("LOG_PATH", "storage/logs/swiftpy.log"),
        },
        "daily": {
            "driver": "daily",
            "path": env("LOG_PATH", "storage/logs/swiftpy.log"),
            "days": 14,
            "when": "midnight",
            "interval": 1,
            "utc": False,
        },
        "stderr": {
            "driver": "stderr",
            "stream": "stderr",
        },
    },
}
```

### Top-Level Configuration Keys

| Key | Default | Description |
|---|---|---|
| `default` | `"stack"` (if defined) or first channel | Channel used by `Log.info(...)` / `Log.channel()` when no name is passed. |
| `level` | `"info"` | Default log level (`"debug"`, `"info"`, `"warning"`, `"error"`, `"critical"`, `"notset"`, or `int`). |
| `queue_size` | `10_000` | Maximum queued records per leaf channel (`0` creates an unbounded queue). |
| `channels` | *required* (`dict`) | Named channel configurations mapped to drivers. |

### Supported Channel Drivers

| Driver | Options | Underlying Target |
|---|---|---|
| `"single"` | `path` (default `"storage/logs/swiftpy.log"`), `encoding` (default `"utf-8"`), optional `level`, `format`, `datefmt` | `logging.FileHandler` (creates parent directories automatically; relative paths resolve against `app.project_root`). |
| `"daily"` | `path`, `days` (`backupCount`, default `14`), `when` (default `"midnight"`), `interval` (default `1`), `utc` (default `False`), `encoding`, optional `level`, `format`, `datefmt` | `logging.handlers.TimedRotatingFileHandler`. |
| `"stderr"` | `stream` (`"stderr"`, `"stdout"`, or any writable text stream object with `.write()` and `.flush()`), optional `level`, `format`, `datefmt` | `logging.StreamHandler`. |
| `"stack"` | `channels` (non-empty list of channel names, including nested stacks), optional `level` | Fans records out cleanly to each unique leaf channel with cycle detection. |

The default formatter uses:

```text
DEFAULT_LOG_FORMAT = "%(asctime)s [%(levelname)s] %(name)s: %(message)s"
```

Override `"format"` and/or `"datefmt"` on any leaf channel if you want custom formatting.

## Using the `Log` Facade & Structured Context

Import `Log` anywhere in routes, services, middleware, or jobs:

```python
from __future__ import annotations

from swiftpy import Log, Request, Response, json_response
from swiftpy.http.router import Router

router = Router()


@router.post("/orders")
async def create_order(request: Request) -> Response:
    payload = await request.json()
    Log.info("Order checkout started", user_id=42, currency="usd", item_count=len(payload.get("items", [])))
    return json_response({"status": "accepted"}, status_code=202)
```

Supported methods on `Log` (and on `ChannelLogger` returned by `Log.channel(name)`):

- `Log.debug(message, *args, **context)`
- `Log.info(message, *args, **context)`
- `Log.warning(message, *args, **context)`
- `Log.error(message, *args, **context)`
- `Log.critical(message, *args, **context)`
- `Log.exception(message, *args, **context)` — logs at `ERROR` with `exc_info=True` automatically
- `Log.log(level, message, *args, **context)` — accepts numeric level or string level (`"warning"`, etc.)
- `Log.channel("daily").error("Payment gateway timeout", provider="stripe", attempt=3)`

### How Keyword Context Serializes & Redacts Sensitive Keys

- Any keyword arguments other than `exc_info` and `stack_info` are treated as structured context:
  - `ChannelLogger` recursively redacts sensitive credential keys (`password`, `password_hash`, `secret`, `secret_key`, `api_key`, `apikey`, `access_token`, `refresh_token`, `token`, `authorization`, `key_hash`, `pepper`, `private_key`, `client_secret`, matched case-insensitively) to `"[REDACTED]"` before formatting or attaching `extra={"swiftpy_context": ...}`.
  - `ChannelLogger` renders positional `%`-style formatting if `*args` are provided, serializes the sanitized context dict with `json.dumps(context, default=str, ensure_ascii=False)`, and emits `<message> <json>` while attaching `extra={"swiftpy_context": sanitized_ctx}` on the `LogRecord`.
- **Bounded Queue Backpressure (`queue_size`):** Each leaf channel uses a bounded `queue.Queue(maxsize=queue_size)` (`10_000` by default; set `"queue_size": 0` for an unbounded queue). If a downstream disk sink stalls long enough to fill all `10_000` slots, stdlib `QueueHandler` drops overflowing records and reports the queue-full condition via `handleError` to `sys.stderr` rather than blocking the asyncio event loop.
- Unhandled request errors and `>= 500` `HttpException` failures logged through SwiftPY's `swiftpy.core.exceptions` logger flow automatically into the active default channel of `LogManager` (for example `storage/logs/swiftpy.log` when `"single"` is in your default stack).

## Using `LogManager` Directly in CLI Scripts or Tests

Outside an `Application`, manage logging explicitly with `LogManager`:

```python
from __future__ import annotations

from pathlib import Path

from swiftpy.logging import Log, LogManager

logging_config = {
    "default": "app_file",
    "level": "debug",
    "channels": {
        "app_file": {"driver": "single", "path": "logs/worker.log"},
    },
}

with LogManager(logging_config, base_path=Path(".")) as manager:
    manager.channel().info("Worker booted cleanly", pid=1234)
    # Or use Log.channel() if bound inside an active Application container
```

For async scripts, call `await manager.astart()` on startup and `await manager.astop()` in a `finally:` block so `QueueListener.stop()` runs off the event loop via `asyncio.to_thread(...)` and flushes queued records before exit.

## Important Defaults & Pitfalls

> [!WARNING]
> **Never shadow Python's stdlib `logging` module:** Inside SwiftPY projects (and especially inside custom packages), keep `import logging` absolute and do not name application files or modules `logging.py` in a way that could shadow stdlib `logging`. Keep your app config inside `config/logging.py` cleanly imported as a config namespace rather than executing relative `import logging` statements.

> [!NOTE]
> **`stderr` vs. `single`/`daily` levels:** Every leaf channel respects both the top-level `level` and its own optional channel `level`. Set `LOG_LEVEL=debug` locally and `"level": "warning"` on `"stderr"` if you want verbose debug logs written to disk while keeping console output focused.
